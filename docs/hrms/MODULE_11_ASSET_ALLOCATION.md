## 4. Module 4 onboarding — equipment task recognises completed handovers

  elsif v_t.task_kind = 'asset' then
    if v_t.asset_assignment_id is not null then
      -- Module 11: the linked equipment must have been acknowledged by the joiner (or confirmed by HR/IT).
      if not exists (select 1 from public.hr_asset_handovers h
                      where h.assignment_id = v_t.asset_assignment_id

## 5. Module 4 exit clearance — inspection, completed returns and sign-off

What 141 already enforces (no M4 change needed): `hr_employee_open_assets(employee)` now returns an asset while
its assignment is active **or** its return is `received`/`inspected` (not completed). 130's existing checks in
`hr_complete_clearance_item` (line ~1439) and `hr_grant_clearance_exception` (line ~1491) therefore already refuse
to clear `asset_return` until every return is inspected **and** completed.

Required M4 change — also require the authorised Module 11 sign-off before `asset_return` is completed:

```sql
-- hr_complete_clearance_item, replace the asset_return check (line ~1438):
  if v_item.item_key = 'asset_return' and p_status <> 'pending' then
    if exists (select 1 from public.hr_employee_open_assets(v_x.employee_id)) then
      perform hr_private.fail('Assets are still assigned or awaiting return inspection. Complete their returns in Assets first.', 'open_assets');
    end if;
    if p_status = 'completed'
       and exists (select 1 from public.hr_asset_assignments a0 where a0.employee_id = v_x.employee_id)  -- ever held equipment
       and not exists (
         select 1 from public.hr_asset_clearances c
          where c.employee_id = v_x.employee_id
            and (c.exit_id = v_x.id or c.exit_id is null)
            and c.cleared_at >= coalesce((select max(a.assigned_at) from public.hr_asset_assignments a
                                          where a.employee_id = v_x.employee_id), '-infinity')) then
      perform hr_private.fail('Record the asset clearance in Assets (missing or damaged items must be acknowledged) first.', 'asset_clearance_required');
    end if;
  end if;
```

## 6. Security and permissions

### 6.1 Purchase cost (`assets.view_cost`) — verified
Database (141 + 141b tests, baseline and combined):
* Cost lives in `hr_asset_financials` — RLS select only with `assets.view_cost`; no write policies; anon has no access.
* `hr_assets.purchase_cost` is always null (trigger `hr_assets_cost_split` checks the permission, moves the value,
  nulls the column). Users without the permission cannot insert or change a cost; editing other fields keeps it.
* `hr_asset_costs(uuid[])` refuses callers without the permission.
* No indirect path: registration events carry no cost (141), audit log needs `audit.view`, `hr_asset_overview`
  and the 112/116 reports contain no cost field.
* Default holders: `super_admin` (implicit) and `hr_admin` (granted in 141). Not granted to payroll, managers,
  employees or the proposed IT role.

UI (code audit of every reference):
* `AssetsPage` loads cost only when `hasPermission("assets.view_cost")`: edit form (otherwise a disabled
  "Restricted" field), asset detail row, CSV export column.
* `saveAsset` strips `purchase_cost` unless the user holds the permission **and** the current value loaded, so a
  user can never overwrite a cost they cannot see.
* Employee Portal and `EmployeeAssetsPanel` never request cost.

### 6.2 Employee isolation — verified (141b, 47 assertions; 141; browser flow)
An employee cannot see or act on another employee's assets, assignments, handovers, damage reports, returns,
document links, history events, clearances, evidence documents, document versions or stored files
(`document_can_read`/`document_object_readable` refuse), and every RPC (`acknowledge`, `report damage`, `edit
report`, `attach evidence`, `request/cancel/confirm return`, `open assets`, `clearance`, `handovers`) refuses with
"not found"/"not allowed". An employee cannot plant their own file on someone else's report or upload to someone
else's profile. Line managers without `assets.view` see no asset records of their team.

Nuance (Module 9 design, not a leak introduced here): a manager holding `documents.view_team` can read the
**documents** of direct reports in non-confidential categories, which includes the three asset categories.
If that is unwanted, M9 can mark them `employee_can_view = true, is_confidential = false` but exclude them from
team visibility (needs an M9 rule change).

### 6.3 Other enforced rules
Server-side transition checks for handover, damage and return states; one active assignment per individual asset
(unique index); units awaiting inspection unavailable; separation of duties (no self-assign, self-confirm,
self-receive/inspect/complete, self-clearance); resolved damage and completed/cancelled returns immutable; history
events immutable; deletes blocked on all asset tables; all new tables audited.

### 6.4 Permissions for a future IT / Asset Manager role
Create as a custom role (`hr_roles`, `is_system = false`) — no migration change needed:

| Permission | Needed for | Required? |
|---|---|---|
| `assets.view` | read register, assignments, handovers, damage, returns, history, overview | **yes** |
| `assets.manage` | register/edit assets, assign, handover confirm, damage workflow, returns, clearance sign-off, exit return checklist; owner of M4's `asset_return` clearance item | **yes** |
| `employees.view` | employee pickers and employee names in every asset list (`hr_employees` RLS) | **yes** (non-sensitive master data only; `employees.view_sensitive` NOT needed) |
| `assets.view_cost` | see/enter purchase cost | optional — grant only if IT records purchases |
| `exit.view` | open the exit screen where the panel is mounted | optional |
| `exit.clearance_it` | own M4's IT-clearance item (permission introduced by 130; its test uses a role `it_admin`) | optional — if IT also signs off IT access |
| `documents.manage` | upload handover / return-confirmation files for an employee (Module 9 requires it for uploads to another profile) | see limitation 8 |
| `documents.view` | open employee-uploaded damage evidence (Module 9 read rule) | see limitation 8 |

`documents.view/manage` are broad (all employee documents). Recommended Module 9 follow-up: allow `assets.manage`
holders to upload and read **only** documents in the `asset_*` categories / linked in `hr_asset_document_links`
(additive policy + register check), so the IT role needs no general document access. The 141b test already
exercises such a role (`assets.view` + `assets.manage`, no cost).

## 7. Private document integration (Module 9) and warranty limitation

* Three categories added: `asset_handover` (HR uploads, employee can view), `asset_damage_evidence` (employee may
  upload to own profile), `asset_return` (HR uploads). `requires_expiry = false`, not confidential, not in the
  onboarding checklist.
* Files are normal Module 9 documents: private `hr-documents` bucket, path `<employee_id>/<document_id>/<v>-<name>`,
  registered with `hr_register_document_upload`, uploaded to the exact registered path, opened via 60-second signed
  URLs with access logged (`hr_log_document_access`). Versions immutable. No new bucket or storage policy.
* `hr_asset_document_links` ties a document to exactly one handover, damage report or return. Linking checks the
  category matches the record kind, the document belongs to the record's employee, and the caller is an asset
  manager (or the reporter, own file, report still *Reported*). Resolved reports accept no new evidence.
* **Limitation — warranty / purchase-invoice documents are not supported**: `hr_documents.employee_id` is NOT NULL,
  so an asset-level document without an employee cannot be stored without a new storage path, which this module
  deliberately avoids. 129 does not change this. Required M9 extension: optional `subject_type/subject_id` (or
  nullable `employee_id` + `asset_id`) with its own read rule (`assets.view`) and storage path prefix; Module 11 would
  then add a `warranty` kind to `hr_asset_document_links`.
